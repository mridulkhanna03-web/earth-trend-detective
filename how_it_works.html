How our data and statistics work

Q1Are we taking region-wise data?

Yes. Every number in the app belongs to one region. We never analyse single map pixels.

A region is a rectangle on the map, set by four numbers: south, west, north and east edge (latitude and longitude). We have 9 named regions (Wisconsin, Central Valley of California, Southern Amazon, Sahel, Indo-Gangetic Plain, Pune, Iberia, Western Cape, Southeast Australia) plus one called "Entire world".

For each region and each measurement we store one number per month. So "Wisconsin, air haze" is simply a list of about 288 monthly numbers (2002 to 2025). In total: 49 such lists, all real NASA data.

Why regions and not the whole globe: the challenge says "most trends… will not be global". Also, a region list is small enough to download by hand in one day.

Q2How does the whole thing work, start to finish?

  1. NASA measuresSatellites and NASA models record a value for every small square of the Earth, every month.
  2. Giovanni averages the regionOn NASA's Giovanni website we draw the region box. Giovanni returns one average value per month as a CSV file.
  3. We save the CSVOne file per region and measurement, named like wisconsin__aod.csv. 49 files, downloaded on 14 Nov 2026. A helper, collect_giovanni.py, names them from the region box inside each file.
  4. Our script packs themgiovanni_to_regions.py reads all files, fixes units, marks missing months, and writes one file: data/regions.json.
  5. The web page loads itThe page reads regions.json once. After that, everything is calculated in the browser. No server.
  6. User picks What, Where, WhenMeasurement, region, start and end year, and whole year or one season.
  7. Months become yearsThe chosen months of each year are averaged into one value per year.
  8. Trend and testsWe fit a straight line, measure how sure we are (p-value), and double-check with the Mann-Kendall test.
  9. Answer in plain words"Rising / likely rising / no clear trend" (same for falling), how fast, how sure, the chart, the seasons, similar places and likely causes.

Steps 1 to 4 happen once, before the demo. Steps 5 to 9 happen live, each time the user changes a choice.

Q4Is the data averaged? How exactly?

Yes, twice. First across space (done by NASA's Giovanni), then across time (done by our page).

Averaging 1: across the region (space)

A region contains hundreds of small squares, each with its own value. Giovanni's "Time Series, Area-Averaged" option turns them into one value per month for the whole box. We do not do this step ourselves; we download the result.

What this means: a region value is the typical value for the whole box. A hot corner and a cool corner cancel out. That is why small, uniform regions give cleaner answers than huge mixed ones.

Averaging 2: months into one value per year (time)

Monthly data goes up and down every year because of the seasons. That yearly wave is much bigger than any slow trend and would hide it. So we turn each year into one number:

  • Whole year: the average of all 12 months.
  • One season: the average of its 3 months. Seasons are Dec–Feb, Mar–May, Jun–Aug, Sep–Nov.
  • Dec–Feb crosses New Year. December of the previous year is counted with January and February. So "winter 2010" = Dec 2009 + Jan 2010 + Feb 2010.
  • Missing month = skip that year. If any needed month has no data, that year is left out, not guessed. Example: Pune air haze has 7 monsoon months with no data (clouds block the satellite), so the Jun–Aug test there has 16 years, not 23. Rainfall ends in September 2025, so 2025 is skipped for whole-year rainfall.
Example. Wisconsin air haze, summer 2015: June 0.18, July 0.24, August 0.21. Year value = (0.18 + 0.24 + 0.21) ÷ 3 = 0.21. Doing this for 2002 to 2025 gives 24 points. Those 24 points are the chart and the input to every test.

Unit fixes done by the script

  • Temperature in kelvin is changed to °C (minus 273.15). The script detects kelvin when the typical value is above 150.
  • Rainfall in mm per hour is changed to mm per month when we run the script with --precip-mm-per-hour.
  • Weekly groundwater values are averaged into one value per month.
  • Giovanni's "no data" code (for example −9999) becomes an empty value.
Note on rainfall. For rainfall we also take the average of the months, so the chart shows "average mm per month in that year", not the yearly total. The trend direction and the p-value are the same either way.

Q5How is the trend computed and shown?

We draw the best-fitting straight line through the yearly points. Its steepness is the trend.
  1. Straight-line fit (called linear regression or least squares). It finds the line that stays as close as possible to all points.
  2. Slope = how much the line goes up or down per year. This is the "how much is it changing" answer. Positive = rising, negative = falling. On screen we show it per 10 years, which is easier to read.
  3. 95% confidence interval = a range around the slope. It says "the true rate is very likely between A and B". Computed as slope ± (a table value × the slope's uncertainty). If this range includes zero, we cannot rule out "no change".
  4. Second estimate (Sen's slope). We take every pair of years, compute the slope between them, and take the middle value. One freak year (a huge wildfire summer) barely moves it. If it agrees with the line fit, the result is solid.

On screen: the chart shows the yearly points and the trend line. Next to it: a verdict in words, the rate of change, the confidence range, a p-value meter, and five small tiles (whole year + four seasons) so the user sees which season drives the change.

Q6How is the p-value computed?

The p-value answers one question: "If nothing were really changing, how often would random ups and downs alone produce a slope this steep?" Small p = unlikely to be luck.

Test 1: t-test on the slope (this one decides the verdict)

  1. Compute the slope (Q5).
  2. Compute its standard error: how shaky the slope is. Points scattered far from the line, or few years, make it large.
  3. t = slope ÷ standard error. This is "how many times bigger is the trend than its own uncertainty".
  4. Look up t in the Student-t distribution with (number of years − 2) degrees of freedom (fewer after the Q7 correction). That gives the two-sided p-value. "Two-sided" means we count surprises in both directions, up or down.
  5. Rule: p below 0.05 = "significant". This is the usual scientific cut-off. We run it twice: once plain, and once strict (Q7). That gives three verdicts, below.
Example. 24 years. Slope = +0.004 per year, standard error = 0.0015. t = 0.004 ÷ 0.0015 = 2.67. With 22 degrees of freedom, p ≈ 0.014. That is below 0.05, so the result is "rising, significant". (The app then applies the stricter check from Q7, which raises p a little.)

Test 2: Mann-Kendall (second opinion)

  1. Compare every year with every later year. Later value higher: +1. Lower: −1. Equal: 0.
  2. Add them all up. Call the total S. A strongly positive S means "mostly rising".
  3. Compare S with what pure chance would give (a formula that depends only on the number of years, with a small fix for repeated equal values). This gives a score Z, and from Z a p-value.

Mann-Kendall only looks at order, not size. So it does not need the data to follow a straight line or a bell curve, and one extreme year cannot fool it. The challenge names both tests; we show both. When they agree, we trust the result more.

The p-value maths is written by us in plain JavaScript and self-checks on page load against known textbook values (for example t = 2.228 with 10 degrees of freedom must give p = 0.05).

Q7How do we handle false alarms?

A false alarm is saying "significant trend" when there is none. Our rule: the false alarm rate of a "confirmed" verdict must stay below 5%. The "likely" level is not covered by this rule and says so on screen. We measured it (table below) and tell the user when to be careful.
RiskWhat we do
Pure chanceThe 0.05 cut-off is what sets the limit: at most 5 in 100 trend-free series may look significant. We measure this by feeding the real code thousands of random series with no trend. Results are in the table under this one.
Years that copy each other (autocorrelation)A dry year is often followed by another dry year. Then 24 years hold less independent evidence than 24. We measure how much each year resembles the one before (a number r, from −1 to 1) on what is left after removing the line. Short records make r look smaller than it really is, so we use a cautious, higher estimate: r + a small-sample correction + one standard error (1 ÷ √n). Then we shrink the "effective number of years" to n × (1 − r) ÷ (1 + r). This widens the uncertainty and raises the p-value in both tests, every time. Example: 24 years with a cautious r of 0.5 count as only 8.
Too few yearsFewer than 8 usable years: the app refuses to test and asks for a longer period.
Lucky start yearA trend can appear only because the period starts in an unusual year. The "Does the starting year matter?" strip repeats the test for each start year and shows whether the verdict stays the same.
Seasons hiding the trendWe test yearly values, not raw months (Q4), so the yearly seasonal wave cannot hide or fake a trend.
One extreme yearMann-Kendall and Sen's slope are less influenced by a single year, but not by a cluster of years at the end. Several unusual years in a row at the end of the record can still create a trend in every test. The start-year strip and the chart itself are the check for that. The app also prints a note when the two slopes disagree.
Missing dataIncomplete years are skipped, never filled with guesses.

Short records with strong year-to-year resemblance go above 5%; no simple test can fix that with so few points, so the app should warn on short periods.

The price. A stricter test misses more real but weak trends. In our trials a moderate real trend over 24 years was found about 75% of the time, against about 92% with no correction. Strong trends are still found almost always.

What changed on 14 Nov. The earlier version corrected only when r was above 0.3. It passed on independent series (4.5%) but gave 12% to 26% false alarms when years resembled each other. That is now fixed in stats.js.

Two honest limits to state on the project page.
  • Many tests at once. The "below 5%" rule holds for each single test. One region shows up to 30 tests (6 measurements × 5 season tiles), so about one can still be "significant" by luck. We do not correct for this yet. Treat a lone significant tile as a hint, and trust results that show up in both tests and survive a change of start year.
  • Our own autocorrelation fix. It is a cautious version of a textbook correction, not the named Hamed-Rao method. We chose it because we could measure that it keeps false alarms under 5%.

Q8What other cases does the app handle?

  • "Not significant" is still an answer. The app says "no clear trend" and shows the range. It does not say "nothing is happening". The challenge asks for this.
  • Wrong measurement for the place. A pair with no NASA file (for example sea temperature in Wisconsin, or groundwater for the whole world) shows "nothing to test". It never shows made-up numbers.
  • Seasons south of the equator. Dec–Feb is summer in Cape Town and winter in Wisconsin. So the app names seasons by their months ("Dec–Feb", "Jun–Aug"), never "summer" or "winter".
  • Similar places. For each region we run the Mann-Kendall test on every measurement and every season. The list of scores (each from −4 to +4) is the region's fingerprint. Two regions are similar when their fingerprints point the same way. We compare land with land and ocean with ocean, need at least 10 shared scores, and show matches of 30% or more.
  • Scenario and causes. Taken from what already happened in the similar region, with written notes. These notes are written by us, not computed, and each needs a source link before submission.
  • Data file missing. If data/regions.json cannot be loaded, the page shows an error message. There is no sample-data fallback any more.

Q9Should we remove the "ask a question" box?

Yes. It is removed from the app. Nothing else depended on it.
  • Your concern is correct. The box only matched keywords. People phrase things in too many ways, and a wrong guess looks worse than no box.
  • The challenge asks for "a short series of questions". Our three menus (What, Where, When) plus the five example buttons already are that.
  • The code is deleted from the app. A copy with the question box is kept outside the project in case the team wants it back.
  • If we revisit it later, the reliable way is an AI model that only fills the three menus, and the user confirms before anything runs. The statistics never depend on it.

The PRD and TRD still list the question box under "Should". That now reads as "parked".

Glossary

Region
A rectangle on the map defined by its south, west, north and east edges.
Area average
One value that stands for the whole region, made from all the small squares inside it.
Time series
The same measurement repeated over time, in order.
Giovanni
A NASA website that makes charts and CSV files from NASA data without programming.
Trend
A slow, lasting rise or fall, as opposed to year-to-year wobble.
Slope
How much the trend line changes per year.
Linear regression
The method that finds the best-fitting straight line through points.
Standard error
How uncertain a computed number (here, the slope) is.
p-value
The chance of seeing a slope this steep if nothing were really changing. Below 0.05 is called significant.
Significant
Unlikely to be luck. It does not mean "large" or "important".
Confidence interval
The range that very likely contains the true rate of change.
t-test
The test that turns "slope ÷ its uncertainty" into a p-value.
Mann-Kendall test
A trend test that only counts whether later values are higher or lower than earlier ones.
Sen's slope
The middle value of the slopes between all pairs of years. Resistant to extreme years.
Autocorrelation
When each year tends to resemble the year before it.
False alarm
Reporting a significant trend where none exists.
Degrees of freedom
Roughly, the number of independent pieces of evidence. Here: years minus 2.
Percentile
A rank from 0 to 100 against the place's own history. 10 means only 10% of past values were lower.
Fingerprint
A region's list of trend scores across all measurements and seasons.
